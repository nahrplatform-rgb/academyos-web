## Startup and update sequences traced in source

**Returning with a compatible downloaded store:** load session from device Keychain → establish same-owner permitted local access → open account/period/journal and saved related datasets → publish the local workspace → run coalesced renewal/account verification → warm missing/changed features → synchronize pending approved personal commands. Existing durable baseline can avoid downloading an entire month on reopening.

**First/new/cleared device:** authenticate → fetch permitted account/current period → create/open scoped protected store → fetch complete saved personal schedule with checkpoints → atomically install baseline → load independent history/features. Not every personal dataset is guaranteed complete before the UI opens, and a native first bootstrap may still have a complete-baseline barrier for editing. This is a useful reference, not the exact AcademyOS target startup sequence.

**Unchanged data:** compare feature digest with completed local digest; skip eligible feature download. **Changed data:** execute its bounded reader; verify source consistency; install completed result, then record completion. Source includes both digest and time-triggered refresh paths; metadata checks are not a proof of zero unnecessary requests.

**Supported personal offline edit:** obtain local lease → compare current local editing basis → atomic encrypted local mutation and queue record → acknowledge local save → active online sync submits sealed whole batch → validate exact receipt → transactionally acknowledge → refresh authoritative baseline. With no current session, upload waits. Conflict, capacity, failed disk write and malformed receipt preserve data and need explicit recovery.

## Limits and risks to carry forward

1. **Different trust model.** A person's own schedule/payroll is different from an academy's multi-role directory of children, roster, contacts and family finances. Reusing local-data mechanics cannot import its personal offline authorization, key handling or data scope.
2. **Local-access expiry deserves scrutiny.** `offlineOwner` verifies the stored lease expiry, while `StagingJournalAuthority.verify` uses a new now+7days in its offline binding. Outer app/session paths recheck the stored lease, but this review does not prove every protected operation is bounded by that exact original expiry. AcademyOS must bind every local access check to one immutable issued expiry, test rollback/clock anomalies and never extend it from an offline reopen. No exploit or hosted security closure is claimed.
3. **Full replacement can be expensive.** Feature hashes and full downloads are a useful first mechanism but do not guarantee low service cost at academy scale. Current in-memory event projection and complete baseline transfers need separate scale evidence; there is no database/query-cost benchmark in this review.
4. **Background does not mean suspended execution.** Scene changes cancel much of the work. An installed iOS app and a PWA both need explicit active/resume scheduling; no promise of continuous work while closed.
5. **History docs can drift.**11October notes say several capabilities remain incomplete; later code and26October note receipts materially extend them. Maintain current source/contract/coverage records instead of copying old completion percentages.
6. **Good failure patterns matter as much as caching.** Missing keys/tampered stores do not justify destructive reset; local-success, pending, conflict and server-confirmed are distinct; sign-out attempts credentials cleanup even if local cleanup fails. Pending data and ordinary rebuildable read projections have different disposal rules.
7. **A reference test is not transfer proof.** The54 passing local tests do not validate Clerk/AcademyOS permissions, browser persistence/eviction, multi-tab writers, offline leases, actual phone interaction or backend traffic. Independent security remains open in both contexts.
