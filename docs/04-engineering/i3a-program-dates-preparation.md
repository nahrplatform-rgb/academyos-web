## Proposed actions and trust crossings

J09-A01 proposed commands: list, context, preview, create, read, reconcile/cancel-before-commit. Browser supplies academy/resource, recurrence intent, expected context revision and operation identity; server derives actor/current authority. Never accept actor, arbitrary branch authority, status=scheduled, session IDs, timestamps or trainer/player bindings from untrusted fields. Preview is side-effect-free authoritative calculation; client-rendered dates never authorize a write. Save revalidates/derives exact dates, compares preview fingerprint/context revision, inserts program+all dates+audit+receipt atomically; no asynchronous partial generation for this bounded range. Read returns only current Owner's permitted draft projection. No privileged key as caller authority. Tables private, no direct authenticated table writes; existing signed/throttled gateway must cover all new functions, including recovery.

Database/server timezone conversion needs deterministic round-trip validation of ambiguous/nonexistent local times against trusted timezone rules; never assume a fixed offset or infer DST correctness merely from JavaScript formatting. Choose and verify the implementation after policy/design decisions; no new dependency justified yet. Test Africa/Cairo transition dates and a non-DST zone; construct examples from the runtime's actual timezone rules instead of hardcoded dates guessed from memory.

## L07 retrieval/freshness and proposed budgets

Critical first view: one private25-row keyset program projection (ID, label, branch/sport, draft state, timezone, date bounds, date count, version); no total count/history/roster/financial joins. Selected program: explicit detail read with at most20 dates; selection of already loaded summaries adds no read. Context request bounded to existing branch/sport/timezone and revision. Preview at most28 days/20 dates, one server call; no daily fan-out. No background polling. Named context switch aborts reads and excludes late response; any current denial removes private data/drafts. Clean return coalesces one relevant read; dirty return preserves input and invalidates old preview. After confirmed create, one selected-detail read; failed follow-up stays confirmed and retries only read. Unknown creates remain original-operation scoped and block replacement/navigation.

Initial budgets to measure, not current performance claims: authenticated useful directory ≤2.5s p95, scoped read/preview ≤1s p95, bounded save ≤1.5s p95 at declared network/region; SQL read≤100ms, preview≤150ms, save≤300ms; directory≤32KiB and detail/preview≤24KiB encoded JSON. Profile50 sequential read samples,10 bounded preview samples, named low-rate stop-on429/error protocol; write/concurrency tests use local synthetic database first. Hosted writes only within accepted slice/environment and no new grants. No billing cost estimate from samples alone. Existing shared limiter configuration must be measured and respected, not raised to meet benchmark. Revise budgets with evidence, do not silently drop failing samples.

Assets: tenant draft program metadata, branch/sport authority, dated schedule integrity and audit/receipts. Crossings: browser/session → app API → signed rate-limited database gateway → private tenant tables/functions. No email/storage/provider callback/offline/export path in scope. Do not disclose foreign labels or object existence in denial.

Detection: existing safe audit/event category and operation correlation only; no raw name/recurrence/identity/token in logs. Operational Owner handles staging failures; audit/privacy retention follows existing policy, no new telemetry or alert subscriptions. Containment: disable new entry/command capability within this slice if a leak is found, preserve records/audits and deny writes; no auth weakening, deletion or broad restoration. Recovery: original operation status/cancellation fence before replacement; confirmed response loss recovers original draft; atomic failure leaves no partial dates; context conflict retains input and requires fresh preview. Rollback app/function entry only after inspecting committed data; no drop/restore over later writes.

## Weekday-specific times — Owner request, 25 October 2026

Recurrence intent now contains up to7 unique selected weekday rules, each with its own local same-day start/end pair. Bind a generated date to exactly its matching weekday rule. Validate each selected pair and each date's timezone conversion; an invalid selected rule blocks the entire preview/save with no partial dates. Unselected editor times do not generate sessions. ## Longer periods — superseding draft engineering proposal, 25 October 2026

Moamen agreed to separating full program duration from bounded retrieval/generation. This replaces the earlier whole-program28-day/20-date assumption and the one-transaction generation approach for longer ranges. The preceding preparation is historical where it conflicts with this section. Connected design approval remains pending; no product code/schema has been started.

Proposed authoritative contract: canonical immutable program revision with full explicit range, up to7 weekday rules and fixed timezone/context version; deterministic count and window manifest. Server validates every window, including future DST gaps/folds, and binds the complete reviewed manifest to the immutable revision. Editing any rule/range/context invalidates the manifest. Never trust client checks, totals, generated timestamps or window-completion flags.

Create should atomically record one intent/receipt plus draft preparation state and durable bounded work, then generate idempotent chunks keyed by program revision/window/date. Replayed work must check payload hashes and unique occurrence identity. Finalization verifies expected count, all manifest windows and current authority/context before marking ready; no incomplete draft appears successfully prepared. A failed or interrupted batch retains an explicit preparation/recovery state, resumes original work and never creates a replacement program by blind retry. Chunk completion and readiness are separate from database command acknowledgement. Owner revocation, stale context, both cancel/commit lock orders and recovery need fresh threat/concurrency contracts. Do not reinterpret stored occurrence times after timezone changes. No asynchronous job/provider choice is made by this document.

Read/preview pages are bounded to28 calendar days/at most28 rows for one program; directories remain25 rows. Totals derive from at most7 rules without iterating the whole period. No full-range JSON/table render, one request per date, or unbounded single SQL transaction. Actual supported date horizon, total job quota, chunk/time/statement limits, hosted usage/cost and expected background load must be settled/measured before dependent implementation; do not market unlimited duration from a permissive local simulation. Existing response/time budgets are proposals to remeasure with28-row windows, not previously proven limits for the revised model.

The design simulation keeps reviewed windows in local memory and combines them only for its simulated receipt; this is intentionally not a production persistence algorithm. An actual preparing/failed/resume progress design is still needed if the implementation uses asynchronous materialization. Local tests cover a92-day/40-date/four-window program, no duplicate/missing boundary dates, later-window DST failure, confirmation blocked until all windows validate, saved/reopened paging and inherited recovery/EN/AR cases. They do not establish durable batching or server resource/security correctness.
