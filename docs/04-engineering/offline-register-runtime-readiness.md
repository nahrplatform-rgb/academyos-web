## Device choice — research direction selected

The preview deliberately simulated unlocking and stored only fictional plaintext. A real browser needs a selected mechanism for reopening encrypted records when the academy sign-in server is unavailable. The first write slice is already Owner/personal-device scoped; the missing choice is **how that device unlocks private local records**, not whether offline work is wanted.

| Choice | User experience | Engineering/security consequence |
|---|---|---|
| Recommended first mechanism: separate local passphrase | Set a separate device passphrase once. When the local store needs reopening after its key is no longer in memory, enter it to read offline. No timer, inactivity lock or per-page prompt. A full refresh/process restart may require it again; do not promise invisible key retention across restart | Derive a wrapping key locally; store only wrapped random data keys plus authenticated ciphertext. Do not use the AcademyOS password or Clerk token as the key. Wrong/missing passphrase cannot silently reset pending work. Fresh verified original-account sign-in plus local unlock is required for quarantined recovery after logout/30day cleanup. Pending work remains retained if verification/key opening fails |
| Alternative to investigate: device/passkey unlock | Aim to use the device authenticator instead of typing another secret | Browser/authenticator compatibility, offline key derivation, same-account binding, recovery and fallback must be proven first. An ordinary sign-in passkey does not by itself prove offline data-key availability. No biometric/device-only guarantee is claimed |
| Automatically accessible same-origin key on disk | Fast automatic reopening | Not recommended as an equivalent to separately protected pending work: scripts running with that origin/key can decrypt. Do not present UI account selection as confidentiality or silently choose this weaker mechanism |

The first choice is a **recommendation, not accepted policy or a new mandatory password already implemented**. Do not re-ask the answered passphrase-versus-passkey question: investigate the selected device/passkey route, then present its supported opening/recovery behaviour before private enablement. No new inactivity timeout,24hour cutoff, pending-edit expiry or backup/export authority is proposed. A separate private unlock/recovery design must be demonstrated if its visible behaviour materially differs from the approved simulated screen.

Browser cryptographic primitives require careful key custody and specialist review; API availability alone is not security assurance. The standard browser API supports password-based key derivation, but parameters and latency must be benchmarked and reviewed rather than copied from an example. [MDN Web Crypto cautions](https://developer.mozilla.org/en-US/docs/Web/API/Web_Crypto_API), [deriveKey/PBKDF2](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/deriveKey). Browser storage may be cleared/evicted; persistent storage requests cannot replace original-outcome discovery or recovery planning. [MDN storage lifecycle](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria). These official references were checked3November; no browser/device security certification is inferred.

## Proposed bounded runtime contracts — not deployed

1. A principal+academy+device+field/schema epoch repository owns encrypted records, complete coverage and protected pending work. Public headers contain only minimal nonsecret version/routing metadata; protect names, statuses, basis, reasons and searchable private indexes. Never persist tokens or raw passwords.
2. Explicit local Save seals one immutable canonical request and a separately encrypted display/basis envelope, then commits ciphertext+local projection+original-ID metadata together. A failed encryption/IDB transaction is unsaved; no server-Saved banner or generic write queue.
3. A scoped sync owner coalesces current online access renewal, reconnect/manual/foreground work and affected invalidation; maximum one command dispatch per scope. Start with no periodic polling. Unknown original operations take priority over new work; background dataset pages yield to the current task.
4. Preserve existing original cancellation and command semantics. A noncancelling outcome action, if chosen, requires a new explicitly versioned signed target, exact actor/academy/event/operation correlation, bounded request/response and no creation of a fence on missing. A count-only receipt cannot be upgraded in the client to an invented full result.
5. Validate current permission, publication/basis and all new-mark versions at dispatch; definitive rejection becomes retained Needs review. Receipt identity and local settlement commit together. Same-ID replay cannot create a second mark; equal/future device time cannot overwrite current state.
6. Logout/30day read-copy cleanup clears ordinary replicas/materialized keys while retaining separately wrapped pending payloads/original identities. Another account cannot open/send them. Known denial hides/stops immediately and rejects late replies. Missing key, cleanup failure, eviction or old schema must be explicit recoverable states, not automatic purge.
7. Real app boot remains a separate contract. A force-dynamic sign-in route plus IndexedDB does not establish a cold offline launch; any service worker caches only reviewed public shell/assets, never blanket authenticated HTML/API/private URLs.
