# EX-09 private Owner register release choices

4 November 2026. The Owner approved this first-pilot scope for implementation: an existing Academy Owner prepares one published register on a personal device. The stored fields are session details, roster names and IDs, and marks and versions. Logout or 30 days without an online access check clears downloaded rows. Pending work stays protected and the original account can recover it through normal sign-in while it has current Owner access. After loss of access, recovery waits for restored Owner authority. This is scope and recovery approval. Activation and independent security review are separate. [Owner decision](../07-handoff/evidence/owner-register-private-policy-2026-11-04.json).

## Current engineering slice

Add a disabled key-release seam and exercise it against a disposable database. A server-issued namespace binds the approved event to a verified Owner, academy and browser installation. The first version reserves one registration for that Owner/academy. A competing device or event cannot silently replace it. Future movement between registers or devices needs a reviewed transition that preserves unsettled work. Registration checks publication. Recovery after event withdrawal can only recover pending context while Owner authority remains; it cannot reopen the withdrawn roster or record attendance. Existing download/dispatch contracts must be bound to this slot before private runtime integration.

The existing Clerk session and exact signed gateway authorize one bounded indexed lookup. Prepare may insert one new record and one audit row atomically. The Node server wraps a random per-registration key with AES-256-GCM and authenticates subject, academy, event, installation, capability, namespace and key version. The private database keeps the envelope only. Repeated or concurrent preparation returns the winning key. A missing/wrong root or corrupt envelope fails closed without replacing an existing key. Disable the new route as the rollback while preserving registered ciphertext. Hosted root provisioning, rotation and key backup/restore are separate. Exercise expired/missing identity, wrong account/role/tenant/device/event, malformed/oversized input, direct database denial, stale signed proofs, concurrent registration and withdrawal/revocation. Record this as local evidence only.

The approved sign-in and offline-register journeys govern. ## Key custody and request ownership

Use the existing Clerk-backed server session and signed gateway to check the current Owner and academy. A bounded server-owned registration record binds the random installation locator to a server-issued opaque namespace and field epoch. The locator is presented as a routing hint. The server independently derives subject, checks the role/scope, and matches the record before releasing any material. Missing/changed subject, device, academy, capability or epoch fails closed. Recheck authority at the key release and canonical dispatch boundaries.

Prefer a random per-namespace recovery key wrapped at rest by a separately scoped server key, with a versioned wrapper and authenticated scope metadata. Avoid an ordinary readable table containing raw material. A scope-derived key avoids a record lookup but ties historical recovery to root retention and makes per-device revocation/rotation harder. The wrapped-key implementation is local. Hosted secret access and the operational rotation/backup plan need review before actual key custody. Never reuse the onboarding signing key, expose the database service role, or derive either local key from a password or token. Rewrapping must preserve original recovery material and old pending ciphertext. Lost wrapping material must surface an explicit recovery limitation. It must never lead to silently generating a replacement key for unresolved work.

Use a versioned same-origin POST with exact field and response limits, no-store, authenticated caller and explicit rate budget. Coalesce one activation/recovery exchange for a verified scope, with a bounded indexed scope lookup. Covered local navigation/reopening makes zero key exchanges. Reconnect submits each pending register through the canonical sender with the original ID and bytes, with explicit reconciliation after an unknown outcome. A version check or confirmed receipt may trigger a bounded refresh only for the affected register. No polling or claim of delivery while the browser is closed. Measure SQL, gateway, limiter and wire bytes in the real environment before setting service-cost expectations.

Before offline opening, the public shell must carry no authenticated response, session credential or roster payload. Permit only declared versioned app assets and a public shell in Cache Storage. The encrypted store retains the minimal prepared namespace. Online identity changes fence old work before new data appears; scope generation protects against late tab/network responses. An unlocked same-origin script can use locally available browser keys. Review script dependencies, CSP, XSS, origin isolation and logging before enabling the route. Browser eviction, corrupted keys and profile changes need explicit recovery messaging. [Browser Cache API](https://developer.mozilla.org/en-US/docs/Web/API/Cache) and [storage eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).
