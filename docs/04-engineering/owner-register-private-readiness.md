4 November 2026. This is the proposed boundary for the first private personal-device register. The approved sign-in and offline-register journeys govern. This packet supplies the remaining choices and tests for LF-P01–LF-P06, IMP-J12-A01 / J12-A01–A03 / S28 / AO and AT-035/036/042/045 / L08 / SEC-J12 and IMP-J16-A01 / L10 / SEC-J16. ## Policy choices to settle before private implementation

| Choice | Recommended first release | Decision or verification needed |
|---|---|---|
| Device and scope | Existing Academy Owner explicitly prepares one eligible published register in a personal browser profile. A random installation locator distinguishes that profile. The verified server binds an opaque namespace to environment, subject, academy, installation, capability and field epoch. The scope picker and confirmation explain what stays on this device. | Confirm this exact scope and personal-device declaration. A browser locator is neither hardware attestation nor proof the device is unshared. Ordinary email/password remains sufficient. Shared or unsupported browsers retain the online experience. |
| Field set | The [exact register field map](offline-register-device-key-contract.md#exact-first-register-data-proposal) is the allowlist. For the read copy, use the one published session's branch/sport/program labels, dates/times, timezone, counts, roster names/IDs and current marks/versions. For recovery, keep only selected-player context, the immutable operation, expected versions and minimal authenticated metadata. | Approve the exact one-roster field set before storing private records. Audit payloads and browser stores for excluded contacts, financial, medical, family and free-text information. Directory, month and three-month downloads require their own reviewed collection contract. |
| Known loss of access | A withdrawn event makes that event's read replica unavailable. A verified account/scope denial fences the whole affected namespace, drops accessible keys and read copies, cancels in-flight work and leaves protected originals. Temporary failures show Unavailable and do not imply revocation or delete recoverable work. | Agree whether the original account should recover if it has lost Owner access. Recommend requiring current Owner authority for ordinary key release. If access is withdrawn, preserve the encrypted original without showing or sending it until authorized recovery is possible. A wider recovery-only permission would need an explicit policy and separate field/key boundary. |
| Verification and cleanup | Start the accepted 30-day replica period from a server-stamped successful check for that scope. On an open after the boundary, hide replicas before attempting cleanup. Logout or explicit removal fences access first, then removes reusable keys and downloads. A failed cleanup retains a fail-closed quarantine and can be retried. | Confirm which successful bounded checks renew the clock. Recommend current authenticated Owner plus matching device/epoch verification only. Browser wall time offline is approximate. Detect rollback against the last recorded observation when possible and defer opening until an online check in that exceptional case. Record the residual clock limit. No idle timer or 24-hour read cutoff. |
| Pending work | Persist encrypted unresolved originals separately across logout or replica cleanup. Normal sign-in to the original account plus current permitted device/scope can recover them. A refused upload remains Needs review. Its capture time is context only. The server decides the deadline and uses current versions. | Confirm the recovery authority above and what a user sees when the original browser store or recovery key is gone. No automatic pending expiry, deletion, key replacement over existing work, or backup promise. |
| Rollout | Keep the current online experience available. Require privacy and independent security review of actual key custody, identity, offline boot and cleanup before enabling any private pilot. | Approve environment and field rollout separately. This packet authorizes no account grant, provider purchase, hosted flags, schema, or promotion. |

## Key custody and request ownership

Use the existing Clerk-backed server session and signed gateway to check the current Owner and academy. A bounded server-owned registration record binds the random installation locator to a server-issued opaque namespace and field epoch. The locator is presented as a routing hint. The server independently derives subject, checks the role/scope, and matches the record before releasing any material. Missing/changed subject, device, academy, capability or epoch fails closed. Recheck authority at the key release and canonical dispatch boundaries.

Prefer a random per-namespace recovery key wrapped at rest by a separately scoped server key, with a versioned wrapper and authenticated scope metadata. Avoid an ordinary readable table containing raw material. A scope-derived key avoids a record lookup but ties historical recovery to root retention and makes per-device revocation/rotation harder. The wrapped-key choice, hosting/secret access and operational rotation/backup plan need review before any server custody is introduced. Never reuse the onboarding signing key, expose the database service role, or derive either local key from a password or token. Rewrapping must preserve original recovery material and old pending ciphertext. Lost wrapping material must surface an explicit recovery limitation. It must never lead to silently generating a replacement key for unresolved work.

Use a versioned same-origin POST with exact field and response limits, no-store, authenticated caller and explicit rate budget. Coalesce one activation/recovery exchange for a verified scope, with a bounded indexed scope lookup. Covered local navigation/reopening makes zero key exchanges. Reconnect submits each pending register through the canonical sender with the original ID and bytes, with explicit reconciliation after an unknown outcome. A version check or confirmed receipt may trigger a bounded refresh only for the affected register. No polling or claim of delivery while the browser is closed. Measure SQL, gateway, limiter and wire bytes in the real environment before setting service-cost expectations.

Before offline opening, the public shell must carry no authenticated response, session credential or roster payload. Permit only declared versioned app assets and a public shell in Cache Storage. The encrypted store retains the minimal prepared namespace. Online identity changes fence old work before new data appears; scope generation protects against late tab/network responses. An unlocked same-origin script can use locally available browser keys. Review script dependencies, CSP, XSS, origin isolation and logging before enabling the route. Browser eviction, corrupted keys and profile changes need explicit recovery messaging. [Browser Cache API](https://developer.mozilla.org/en-US/docs/Web/API/Cache) and [storage eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

## Evidence needed before the enablement checkpoint

- Current verified Clerk session, active Owner and exact device/academy/field epoch release. Refuse wrong account, second academy, wrong role, revoked scope, expired session and tampered binding before exposing key material. Exercise concurrent registration and late release after logout.
- Trace server key custody, IAM/rotation, no-store and payload/log hygiene. Show that a remaining device key alone cannot decrypt quarantined work. Verify renewed current authority can recover exact originals without bringing back deleted read copies.
- Exercise 30-day boundary, backwards clock, expiry/cleanup failure and cross-tab fencing. Distinguish event withdrawal from membership denial. Confirm interrupted cleanup, missing assets, incompatible versions and storage eviction remain safe and explainable.
- Measure first prepare, unchanged and changed checks, restart, reconnect, refused replay and realistic provider costs. Run the applicable working-day cases across actual authenticated roles/devices separately from synthetic fixtures. Obtain Owner working acceptance and independent security evidence independently.

Follow the [device and recovery contract](offline-register-device-key-contract.md), [local data plan](../06-delivery/local-data-and-sync-plan.md) and [working-day acceptance](../06-delivery/academy-working-day-acceptance.md). This is a design recommendation. It creates no key store or endpoint and enables no private behavior.
