## Candidate mechanism to prove

- A random non-extractable browser key persists through IndexedDB structured cloning. It provides automatic local encryption, not independent protection from scripts running with that origin. No password, bearer token or WebAuthn credential becomes the local key.
- Read replicas use a separate local read key. Pending intent has a random data key with two wrapping layers: account/device-bound server recovery wrapping, then the local device key. Distinct purposes/scope/schema/operation identities are authenticated with each ciphertext.
- While an already verified personal-device store is active, a non-extractable imported recovery key can be kept locally for automatic offline reopening. Honest logout/30day cleanup removes read keys/replicas and this cached recovery key, increments a durable fence and retains only pending ciphertext, wrapped keys and minimal original identifiers.
- After cleanup, the local device key alone cannot decrypt pending work. Normal sign-in to the original account must retrieve the correct account/device/academy recovery material; another account's valid key cannot unwrap it. A late old key response or old transaction must fail the durable fence check.
- Creation, encrypted record writes and cleanup acknowledge only after successful IndexedDB transaction completion. An aborted transaction or missing/corrupt key must not look like Saved or silently reset existing pending work. Page reload/process restart and unsupported/evicted storage are distinct cases.

This is envelope-encryption research. The isolated server supplies fictional account-bound recovery keys from process memory using test-only identity; it is **not Clerk authentication or reviewed server key custody**. No equivalent endpoint/key exists in the working app. A production-shaped design needs current verified identity/membership, exact registered device/scope binding, protected server key storage/rotation, same-origin/no-store/rate/response bounds and denial/recovery evidence before private enablement. Existing app API/SQL authorization is unchanged.
