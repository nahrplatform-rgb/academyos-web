## Boundary and connected behavior

Today the app checks Redis but a caller with its own valid JWT can reach the public RPCs directly. Require a server-only, short-lived HMAC gateway attestation in the existing private `verified_subject` helper. It binds the current JWT subject, actual PostgREST method and RPC path; purpose is domain-separated from recipient/delivery proofs. All ten authenticated entry points (eight M1 and two legacy identity/membership functions) already reach this helper, including nested calls. Keep current role/tenant checks, private-table grants, RLS, transaction/lock/time bounds and receipts. Anonymous delivery retains its separate signed worker protocol.

The API also retains a separate 60-read/10-write entry budget before recipient/provider lookups. It uses a different prefix so a request is not double-charged against one counter; both budgets must permit the call. This adds one bounded Redis check per authenticated request and prevents recipient verification calls from escaping the resource budget. The shared server database transport spends the existing 60 read / 10 write requests per actor per minute before signing or sending a user RPC. Invitation acceptance is a write; review is a read. Legacy bootstrap is a write. Denied and failed RPC attempts consume the external Redis budget, even when the database rolls back. Replays still use the original operation ID and budget; a lost response is reconciled after the budget recovers. Existing EN/AR limited/unavailable/refresh states apply; no new screen or business rule.

Public invitation exchange gets a 30/minute network-source budget and 300/minute staging-wide budget before cookie encryption. On Vercel use its overwritten `x-vercel-forwarded-for` only, validate a single IP, HMAC it with a domain-separated server key, and fail closed if missing/invalid. Local development uses one fixed local bucket and ignores supplied IP headers. No IP, proof, JWT, token or private payload is logged/stored in business rows. Redis keeps short-lived pseudonymous counters with analytics disabled, no retries and existing deadlines. These controls bound expensive downstream work; they do not make internet request volume or Redis billing universally bounded, nor replace provider network/DDoS protection. Shared networks can share the exchange budget; keep it independently tunable through a reviewed change.

Proofs never enter browser responses or cookies. Captured server-to-database attestations would be replayable within their 30-second lifetime for the same subject/path/method; they are not body signatures, membership assertions or reusable browser credentials. TLS, server-only key custody and no header logging remain required. Current database authorization still validates each actual operation, including membership revocation. No service-role app client, public helper grant, schema exposure or provider subscription is added.

Rejected: transaction-local counters, because failed/rolled-back requests erase them; unbounded direct RPC access, because it bypasses Redis; privileged service-role replacement, because it would discard caller authority. A platform pre-request hook is unnecessary because every current authenticated entry point already shares the helper. New public functions must use it and be covered by the entry-point inventory test. Storage/Realtime do not inherit this control; existing private/denied access stays unchanged.
