## Implementation contract

1. Retain `owner_register_keys` and `x19_owner_register_key_v1` unchanged. Add a versioned key registry and signed x23 key function for distinct `(subject, academy, event, installation)` scopes. Keep the new key route closed by default behind `LOCAL_REGISTER_MULTI_SCOPE_ENABLED`; enable only in declared local fixtures and after the reviewed additive backend is ready. Each new scope receives an independent wrapped random key and namespace, using the existing purpose-bound wrapping root and authenticated metadata. An exact matching legacy registration recovers its original envelope; it is not re-encrypted or copied to another installation. If older/newer clients independently registered both kinds of envelope for the same tuple, recovery selects the explicit original namespace; never silently switch protected work to the other key.
2. Keep one exact registered tuple at download/dispatch. The existing bound-transport check may recognize either the matching legacy row or the matching new row, retaining current Owner, event, subject, device and namespace checks and the existing lifecycle lock. The new key RPC needs explicit signed-gateway allowlisting, authenticated-only execution and the same response/input limits. Never use a client-supplied role as authority.
3. Introduce per-event v2 local locator keys. Preserve a matching v1 locator in place for its old event, including its generation, namespace and originals. New-event preparation creates a separate v2 entry; it must not rewrite a different v1 or v2 locator. Make event selection explicit in normal Attendance, cold startup, prepared panels and the original sender.
4. Preserve per-academy locking while enumerating all compatible locators for account/capability cleanup. Logout, known denial, interrupted cleanup and30-day retention keep their existing fencing and protected-original behavior across every entry. One malformed/failed entry must not silently expose data or discard another entry. Cross-tab notifications must target the selected event and retain account-change fencing.
5. Preparation remains one bounded selected register at a time, through the existing personal-device path. Do not add unbounded roster/month preloading, new fields, another worker, an extra unlock or a universal write queue. Existing quota/storage refusal remains honest; pending work must never be evicted to make room. Supporting more registers does not imply every role/module has offline support.
6. Every local acknowledgement and sync uses the existing immutable original and all-or-nothing register command. Current recording window, versions, membership and publication still decide server acceptance. A fresh namespace is not permission to replace an unknown original for the same event. Keep all earlier namespaces recoverable.

## Required proof

- Two published events in the same academy can prepare distinct scopes on one personal installation; both reopen through their ordinary URLs. Saving/reading one does not alter the other's locator, key, rows or original.
- A matching legacy registration/locator still recovers byte-identical material and protected originals after adding new entries. Legacy x19 behavior remains unchanged.
- Repeated/concurrent same-scope preparation creates one envelope and one audit. Foreign account, role, academy, event, device/namespace combinations, unsigned/stale proofs and malformed replies still fail closed. A different installation may create its own *new* scope only through current Owner preparation; it cannot recover another installation's scope.
- Multi-entry cleanup, interrupted cleanup, denial, account switch and late responses retain all existing privacy/recovery fences. Pending and unknown originals remain isolated and recoverable.
- Lost replies/restarts/reconnect retain the same save IDs and terminal server results. Distinguish401 from403/410. Preserve canonical online fallback where no protected original exists.
- Run real key/transport and normal Next/Chromium/IndexedDB/disposable-PostgreSQL tests. Preserve meaningful existing negative assertions; revise only the explicitly changed same-academy preparation expectation, with new independent recovery/refusal assertions.
- After local proof, apply only the reviewed additive migration to synthetic staging with pre/post legacy-key/attendance/original fingerprints. Preserve rows on rollback/forward repair; never drop keys to undo rollout. Local code can be tested against this backend before a later coherent Owner-controlled release. Actual connected save/reopen/sync and installed-device evidence remain separate.
