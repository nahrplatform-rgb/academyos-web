## Outcome, scope and authority

An existing Academy Owner on an approved personal browser profile opens the normal Players and Calendar routes from permitted prepared data, online or offline. First entry prioritizes the requested task. It then prepares the directory and current month in bounded pages, followed by the next and previous month. Repeat visits reuse complete compatible generations and check quietly for changes. A changed collection replaces only its affected generation. Missing data, failed sync and changed authority remain distinct.

## Versioned transport and coherent completion

Use versioned, purpose-bound actions through the existing same-origin authenticated signed gateway. The closed first implementation uses `/api/workspace-download` with `manifest`, `page`, `resume` and `complete` actions; its exact wire/authority contract and evidence are in the checkpoint above. Do not silently reinterpret the legacy list/cursor responses. Repository and normal-route interfaces below remain to implement.

1. **One workspace manifest.** Derive subject and current Owner/setup/branch from the server. Verify the exact installation/capability/field epoch. Return minimal scope, server time, branch-local today, each requested collection/window identity and its revision. An unchanged check uses indexed metadata, not a full dataset hash or count on every focus. Reuse requires matching collection/window identity, field epoch, scope and revision plus an actually complete local generation; a matching revision alone does not cover a newly opened month. The current-month anchor must be server-resolved at first online opening and on a month/timezone change; offline time is labelled last checked.
2. **Monotonic collection revisions.** A new reviewed migration increments transactional collection revisions for every projection-affecting change. Directory covers player insertion/removal/name/branch and relevant branch labels. Calendar covers ready program/date/time/state, date-plan capacity/roster count, publication heads/events and relevant context labels/timezone. Inspect all canonical writers and add future-write regression coverage. Failed writes must not expose an intermediate revision. Setup/scope/field changes also change the compatibility epoch. An academy-wide revision per collection is acceptable initially, but unrelated-month changes can cause extra bounded replacement; measure that cost honestly.
3. **Same-snapshot page.** Read expected revision, first bounded rows and authoritative total in one coherent statement snapshot or an explicitly verified transaction/lock protocol. Carry that total in the signed chain. Later pages verify the same revision and read a bounded indexed page; they need not repeat a full count or digest. Unchanged manifests do neither. Do not perform a revision lookup and later row read at READ COMMITTED and call them one snapshot. Current authorization still runs per request. Recheck/reject changes before returning a completion proof. Avoid a long transaction spanning browser requests or an unbounded server-side materialized snapshot service. Measure first-page count, later-page work and final verification separately.
4. **Signed continuation chain.** Bind purpose/version, subject, academy, installation, capability, field epoch, query/window, expected revision, stable sort position and accumulated progress to the continuation. A page cannot be transplanted to another month or account. Directory order is UUID. Indexed Calendar transport order is scheduled date/start time/program/original day; the normal UI retains its existing display order. The backend parity check compares canonical rows/instants with the legacy Calendar, not arrival order. Enforce strict monotonic cursor progression, duplicate rejection, exact counts and bounded bytes. The implemented continuation lifetime is 600 seconds; explicit `resume` rechecks current authority, scope and revision and can renew compatible progress without rescanning its prefix. Changed progress restarts only its incomplete collection. Expiry never deletes a completed replica or original operation, and these local tests do not establish a slow-network completion percentile.
5. **Atomic local import.** Store each verified encrypted page and checkpoint together under a staging generation. Partial downloads can resume but never replace the currently complete generation or advertise Complete. Verify the final chain, total and current revision, then publish rows/index/coverage in one local transaction. A subsequent server change is handled at the next sync; the receipt proves a coherent checked version, not permanent freshness. Zero-row completion has an explicit proof. Abort/corruption/quota failure retains the last valid generation.
6. **Removal/replacement.** V1 uses a versioned bounded replacement when a collection changes; it is not a delta feed. After complete commit, records missing from that generation disappear, including moved-out/cancelled/withdrawn results according to the existing projection. Overlapping month coverage cannot resurrect an older version: compatible revisions and generation ownership determine the visible row. Rebuild overlapping affected windows together or suppress older overlapping coverage until coherent. Known authority/scope loss fences the affected namespace immediately. No cross-scope tombstone payload or new server change-log retention is introduced. Later sparse delta support needs its own version, retention and measurement evidence.

This protocol is an engineering design for a collection with concurrent writers. It does not use player table versions, setup version, timestamps, client counters or a successful last page as proof of complete multi-page consistency.

## Storage, identity and account lifecycle

- Introduce a distinct typed Owner-workspace capability/namespace and field epoch. Reuse automatic non-extractable browser-key and server-wrap primitives after verifying their exact bindings. Keep the register slot and pending-key registrations intact. New capability provisioning and account-fence coverage need explicit tests; an existing register namespace cannot authorize unrelated directory data. Reuse the accepted personal-device choice where compatible; an engineering namespace is not another routine setup/unlock prompt.
- A successful key release proves its current account/capability authorization, not that downloaded rows still match the current dataset. Renew a completed replica's verification time only after a matching scope/revision manifest or coherent completion. Keep these timestamps separate. The first backend key registry uses a distinct namespace; actual cryptographic wrapping/release for that capability is not proven by its synthetic test envelope.
- One protected account/academy/device repository owns encrypted records, completion manifests and query indexes. Small decoded working sets support the current task; complete disk coverage does not require all records in RAM. Compare an encrypted chunked search index with bounded decryption on representative datasets before selecting the implementation. Names/prefixes must not appear as readable IndexedDB indexes, localStorage, URLs, logs or cross-tab messages. A non-extractable web key does not prevent an unlocked same-origin script from using it.
- Keep automatic reopening with normal account sign-in. No new passkey, passphrase, inactivity timer or 24-hour cutoff. Retain existing successful-online-check based 30-day replica cleanup and explicit logout/removal. Extend cleanup to every dataset capability, fence first, reject late imports and fail closed on cleanup error. Pending register originals remain separately protected and recoverable only through the original account with current authority.
- A temporary timeout/503 is not revocation. Keep compatible prepared data with Last checked/Offline feedback. A verified denial, account change, incompatible epoch or expired replica cannot become an allowed offline fallback. Offline devices cannot discover immediate remote revocation; record this residual limit without adding an unaccepted idle lock.
- Use a public, versioned offline shell and an internal normal-route client router. Never blanket-cache authenticated HTML/API responses or identity URLs. Deep link/reload must reach the same Players/Calendar screen from that shell; a dedicated register fallback is not completion. Distinguish identity initialization/network failure from an explicit logout or confirmed account/authority change: a permanently loading identity SDK must not block the accepted prepared-data path. Local opening uses the protected last-verified namespace within its accepted lifecycle, never a fabricated fresh server session. Inspect the existing service-worker/offline route before deciding whether a new public shell version or a bounded normal-route continuation is safer. Prove server/account checks on reconnection.

## Scheduling, budgets and visible feedback

| Scenario | Declared target; validate before claiming achieved |
|---|---|
| First entry with no compatible replica | Load the requested useful task first. Coalesce current identity/context and one workspace capability/manifest exchange where safe. Then one background collection page at a time; active navigation preempts it. Prepare current month and the permitted directory, then next month, then previous month. Never hold Today behind three complete months. |
| Covered local search/filter/selection/month switch | Zero operating API calls and zero key exchanges for the action. Read the permitted local query; preserve scroll/selection/focus and draft input. No disguised server search on each local keystroke. |
| Warm navigation with current compatible data | Render locally. A coordinated freshness check may run according to the explicit lifecycle policy; it must not clear the visible collection or mount a second whole workspace. Count route/assets/auth separately. |
| Resume/reconnect/unchanged reopen | Coalesce one manifest check per affected scope with concurrent signals and pages. Download zero dataset pages when revisions match. No default polling, Realtime subscription, per-row check or change-check on every click. Define a short coalescing window from real traces; no unmeasured maximum revocation-detection promise. |
| Changed collection/window | One manifest plus bounded pages and one completion verification, with background status in the top bar. Do not clear the old compatible generation during download. Current actions still verify live authority/version at their canonical boundary. |
| Offline launch/use | Zero network is required for compatible prepared reads. Show Offline and exact missing coverage without repeated reopen/prepare/sync buttons. On the approved supported register writer, Saved on this device and Synced remain separate; no new generic offline queue. |
| Failure or denial | Retry only the failed scope without discarding the task or pending work. Known denial removes private access; preserve only safe structural context. Unknown write outcome reconciles the original ID before any replacement. |

Page targets: retain directory maximum 25 rows and Calendar maximum 50 rows; introduce an explicit per-page payload budget (at most 24 KiB of rows, final envelope less than 32 KiB). Any reduced page must advance the signed cursor. Total rows come from the authoritative snapshot, not the loaded page. Background work yields after a bounded page and records progress. Dataset count/bytes, storage headroom and user-visible coverage must be known; large datasets pause honestly on capacity failure rather than silently truncate. Set the tested size/capacity profile from measurement, not a new arbitrary player limit. Query timeouts, rate controls, signed caller and per-response bounds remain in force.

Initial download needs at least `max(1, ceil(P/25)) + sum(max(1, ceil(Cm/50)))` page reads, **a lower bound** when byte limits reduce a page. Even an empty collection has one page before its explicit zero-row completion. P is all permitted directory summaries; Cm is each of the three 42-day grids and includes overlap unless deduplicated by a later verified transport. Manifest/capability/completion/auth/limiter/SQL work are additional. Unchanged reopen saves those page downloads, not all service requests. Changed v1 collections can retransmit all their scoped pages. No pricing, latency or cost savings is established by this arithmetic.

Use one scoped cross-tab leader with failover, transactional generation compare-and-swap and nonprivate invalidation hints. The leader may yield to the active task. Page interruption resumes only a compatible chain. Do not rely on a closed/suspended browser running sync; active/resume behavior is sufficient for correctness. Connection feedback reflects actual API health and pending scope state, not only `navigator.onLine`.
