## What still needs engineering proof

Ordinary account sign-in establishes identity; it does not itself provide an offline encryption key. Investigate automatic browser key management with minimal retained fields. A non-extractable key stored by the same origin is **not equivalent to an independently protected authenticator**: same-origin scripts with access to that key can use it. Current-account checks and merely labelling a database with an account ID do not provide cryptographic same-account quarantine after logout. Design and test that recovery boundary explicitly; if it needs account-verified server key release, specify key custody, request cost and failure/recovery before implementation. No weaker protection is silently accepted because the device is personal.

Primary references checked3November: [WebCrypto key generation/non-extractability](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/generateKey) and [WebCrypto key-management cautions](https://developer.mozilla.org/en-US/docs/Web/API/Web_Crypto_API). They describe primitives and limitations, not proof of this future implementation.

## Engineering and security work before private enablement

1. **Automatic key management:** investigate a browser-managed non-extractable cryptographic key and authenticated ciphertext, with distinct read/pending key lifecycles. Creation/reopening must require no passkey enrollment, second password or per-page prompt. Do not derive a key from an email address, persist a login password, intercept Clerk password entry or use its bearer token as a wrapping key. The exact storage/wrapping/recovery mechanism must be proven with fictional data before app enablement. This is a candidate engineering design, not an accepted security guarantee.
2. **Real account binding:** persist verified scope separately from navigation state. Changing principal/academy, known denial or logout immediately drops accessible keys/private projections and rejects late callbacks. AAD bound to an account string is useful tamper protection, **not proof of fresh same-account verification**. The product must specify and independently test the same-account recovery/key-release boundary; client UI hiding is insufficient. No server key custody or backup service is silently introduced by this recommendation.
3. **Protected pending recovery:** read cleanup must not delete the pending envelope, original packet, nonce, key reference or recovery metadata. Recovery failure retains those bytes. A missing/corrupt key cannot be repaired by making a new key over the old data. Browser/profile changes, storage eviction and recovery after expired Clerk sessions need explicit supported/unsupported outcomes. No guarantee that uncommitted work survives browser eviction without a separately approved backup mechanism.
4. **Concurrency and integrity:** ciphertext, original intent, local projection and coverage commit transactionally before local Saved acknowledgement. Receipt validation/settlement commits transactionally. Use one scoped sender with generation checks; a lock coordinates tabs but never authorizes a write. Reuse current server checks/atomicity and terminal fences. [Runtime mapping](offline-register-runtime-readiness.md).
5. **Platform evidence:** retain the successful PRF diagnostic and its untested physical cases as historical research. Mandatory passkeys were rejected; those missing PRF/provider tests are not a prerequisite for a different login-only mechanism and are not relabelled as passed. The new automatic-key path needs its own actual browser/restart/offline/denial/cleanup/quarantine tests, including unsupported/blocked storage and missing keys.
6. **Security gate:** review XSS/dependencies/CSP and key exposure in an unlocked origin, correlatable headers, private indexes, same-account recovery and denial/cleanup failure. WebCrypto/IndexedDB and device verification alone are not an independent audit. Only fictional data until the relevant gate passes; real child/customer records remain prohibited.

Request/experience target for that engineering design: key provisioning or account-verified recovery is coalesced at the appropriate sign-in/store-open boundary, never one extra key request per page or row. Normal navigation uses the permitted local repository; current server checks before sync remain. Measure setup/reopen, unchanged return, offline use and recovery separately; no achieved request savings or silent background execution guarantee is claimed.
