# I3c — program-wide private planning with individual dates

27 October2026. **Recommendation for Owner decision; not accepted policy.** Moamen requested both whole-program and individual-date planning, then instructed engineering to proceed with the best option. This authorizes preparation of a concrete recommendation and connected design. His I3b working-feature reply requested an improvement; it was not working-feature acceptance. Existing I3a and earlier journey acceptances remain valid within their reviewed scope.

## Recommended outcome

Programs → open saved ready program → **Plan the program** → select the whole saved period or a smaller explicit date/weekday subset → set capacity, optional eligible same-branch Trainer and existing fictional players → inspect exact dated changes → apply reviewed work → reopen results. **Plan this date** remains available from each dated row and uses the existing atomic I3b journey. A whole-period action does not impose a28-day program limit; bounded pages and execution batches are engineering controls.

## Recommended policy requiring explicit acceptance

| Choice | Recommended behavior | Why / alternative |
|---|---|---|
| Authority and effects | Current active Academy Owner, existing academy/initial branch and ready private draft program only. Fictional staging data. Existing Trainer eligibility, positive capacity, duplicate and same-academy UTC overlap rules apply on every date. | No new Manager/Trainer/family visibility, appointment grant, notification, fee, attendance, time/recurrence edit or publication. |
| Selection | Whole saved period by default, explicit optional smaller range and weekday selection. Preview lists every targeted date; full scope is frozen by exact saved-date identities and versions. | A selected day is a date, not a newly generated recurrence. New/changed dates after review require a new review; no hidden inclusion. |
| Routine plan | One capacity/optional Trainer/fictional roster for selected unplanned dates, with optional weekday-specific choices. Weekday settings are resolved to exact dates before confirmation. | Default same values avoid repetitive work. A weekday-specific row must not silently inherit later changes to another row. |
| Existing date plans | Preserve every existing dated plan by default, show it as **Preserved individual plan**, exclude it from writes and show its current summary. | No automatic merging/replacement/removal of existing rosters. To change it, open **Plan this date** and review explicitly. Whole-program replacement of already planned dates is deferred rather than hidden behind a broad overwrite checkbox. |
| Snapshot semantics | Apply a reviewed snapshot to selected currently unplanned dates; there is no live inherited default. Later individual edits affect only that date. | Changing a program proposal does not silently change dates already saved, including prior program-apply results. Future reapply/propagation needs an explicit affected-date/replacement contract. |
| Conflicts | Review shows ready, preserved and blocked dates with reasons. Blocked dates remain unchanged. Owner explicitly confirms applying the displayed ready subset, or revises the proposal before applying. | Never quietly drop a player/Trainer, overbook, shift a time or claim all dates succeeded. Alternative: block the entire program until every target is valid; safe but one bad date prevents all progress. |
| Large operations | Resumable bounded execution, with each date's plan/roster/audit atomic. Confirmed dates remain saved if later dates fail. Stop on newly detected conflict/staleness or authority loss; show exact completed and remaining dates and require review for the remainder. | This is explicitly a partially completable program operation, not a whole-program atomic promise. Large all-or-none transactions hold academy lifecycle/conflict locks too long and do not match unlimited-period recovery. |
| Resume and retry | Reopen original operation; show saved/remaining/failed dates. Unknown outcome uses **Check original operation** before any replacement. Resume revalidates current Owner, people, versions and conflicts. | Reuse original operation/date identities, avoid duplicate roster effects. Previously preserved dates never enter the write set on retry. Cancellation stops future work, preserves completed dates and reports its exact scope. |

Example:40 dates,1 already individually planned,2 blocked by overlap → preview37 ready,1 preserved,2 blocked. Owner may apply37 explicitly. If12 save before interruption, show12 saved/25 remaining/1 preserved/2 blocked. Reopen/resume original operation; do not describe this as40 planned or roll back the12 silently. If all targeted dates already have plans, offer date inspection; no empty “successful apply”.
