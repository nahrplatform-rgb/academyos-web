## Connected interaction

1. **Training / Programs.** Existing saved program summary retains full period, per-weekday times and ready state. Primary **Plan the program**, secondary **View dates**. No program-planning action on an incomplete program. Published/operational controls remain absent.
2. **Program planning / Choose scope.** Readable whole-period summary; optional range/weekday subset. Explain existing date plans will be preserved. Separate collapsed “Different choices by weekday” editor. Show capacity, optional Trainer and bounded player search/selected-roster builder using existing shared controls. Clearing a field is explicit; no guessed capacity. A Trainer search failure is not an empty candidate list.
3. **Review dated changes.** Summary counts ready/preserved/blocked; actual date rows show branch timezone/time, current versus proposed capacity/Trainer/roster count, changed-player detail on demand and conflict reasons with only authorized fields. Filter by status; stable pagination, all scope accounted for. Counts alone do not substitute for dated preview. **Inspect individual plan** opens current I3b date details and preserves return context. Changed proposal invalidates the review. No preselected conflict waiver.
4. **Exact confirmation.** Any blocked included date disables save for the whole change set. Once resolved: “Save39 dates together; preserve1 individual plan.” A checkbox confirms exact scope. Button **Prepare39 dates** begins private resumable preparation, followed by **Save39 dates together** after final readiness. All-preserved has inspection actions and no apply button.
5. **Preparing / paused / committing / unknown.** Show private preparation progress explicitly separate from saved dates:12 prepared of39,0 saved. Resume original preparation; prepared data is never the effective roster. Final save activates the complete reviewed change set atomically. Any final failure leaves all dates unchanged. Ambiguous response offers **Check original operation**, resolving all or none. Revocation clears private projection and blocks activation. Cancellation before final commit prevents all changes; after commit no undo is implied.
6. **Result / next action.** Show all reviewed changes saved together, or none changed. **View dates**, **Open saved plan**, or **Correct and review again**. Owner-only draft state remains prominent. Individual save updates only its date; later program proposals preserve it by default. No synthetic success toast for blocked or preserved work.

Desktop retains sidebar → program/date work list → contextual inspector; no nested inspector stacking or OS window controls. Phone uses full-width scope/review/detail steps with consistent Back; return restores program, scope, filter/page and selection. EN/AR translations include counts, all-or-none and preparation wording, timezone and status labels; use logical layout, bidi-safe time/code,44px phone targets and keyboard focus on changed step. Reuse `WorkspaceShell`, `WorkspacePanes` and native controls. Prototype simulations, if built, must be visibly labeled and never use actual account data or provider calls.

## Trust boundaries and bounded reads

Current identity → same-origin staging API → named bounded caller transport → current Owner/academy/branch/ready program → private proposed snapshot/job/dated planning/audit. No cached permission or public RPC execution alone is authority. Reuse existing gateway/limiter, canonical Trainer lifecycle lock order, UTC half-open conflicts, version checks and direct-table denial. Extending trusted RPC allowlists requires exact route/proof tests. No generic privileged proxy or internal HTTP loop impersonating the Owner.

Proposed retrieval: program/scope summary independent of first dated page; dated preview25 rows plus sentinel, stable saved-date order/cursor; conflicts/current-roster details on demand, each25 rows; candidate search25 plus sentinel with latest-query cancellation; request<=8KiB and response<=24KiB per ordinary page. Large selected rosters are private staged selections with bounded edit requests and exact count/version, not client-fetched academy directories. Freeze proposal and date-set identity server-side; bind actor/academy/branch/program/scope/proposal fingerprint. Cursor/key includes that full scope, never only program ID.

Private reads no-store; current permissions rechecked on each read/write/continuation. Revalidate people/date versions and cross-date conflicts on execution. Any materially changed eligibility/scope, version or newly blocked date blocks activation of the entire proposal and requires fresh review. Previously committed operations remain immutable history. UI may show that its reviewed state is stale; it must not assert it is still conflict-free. Poll only while visible/active, coalesce focus/reconnect, back off on failures, no automatic provider write merely from rendering. Review token, expiry and server job processing mechanism are engineering decisions to validate; they cannot broaden scope or leave authority cached for later processing.

## Atomicity, recovery and migration design criteria

Preserve the entire reviewed change set—every date's capacity/Trainer/roster, version, history, operation result and audit—as one atomic live transition. Private preparation can be bounded/resumable but no reader may treat prepared rows as active plans. Evaluate a versioned immutable prepared manifest with atomic activation pointer versus one staged-to-live transaction, against existing I3b reads/writes, overlap checks and canonical lock order. No architecture is declared implemented or proven by this design.

Final activation must serialize with existing per-date saves, other program activations, Trainer lifecycle and current Owner membership; revalidate every target version plus current people and actual UTC conflicts. No version check can be split into unprotected batches before activation. If necessary conflict validation requires an unbounded final scan, measure it and revise the engineering approach, not the all-or-none business rule. Same-operation/different-payload conflicts. Unknown activation reconciles the complete original operation. Cancellation and activation share serialization: cancelled means no effective changes, committed means all expected changes; never a cleanup loop deleting already committed plans.

Measure20/40/100/1000-date and large-roster activation/read/individual-edit behavior before promising supported scale. Keep current3s statement/2s lock ceiling as a starting constraint, not a reason for silent timeout increases or partial success. No arbitrary28-day duration or25-player program cap. If safe atomic activation cannot meet the scope/budgets, report the measured limitation and present a concrete engineering tradeoff before dependent implementation. Rehearse migration against a restored encrypted staging backup; preserve existing date plans/history and fail closed if any reader has not adopted activation semantics. No production or new service authority.

## Test and performance acceptance plan

- Policy: whole period, smaller subset, weekday-specific values; exact target counts; preserve existing plans; all-preserved/all-blocked empty action; date edit remains independent; program retry cannot overwrite it.
- Correctness: every committed date matches its review; all reviewed targets or no change; deterministic duplicate/overlap/capacity checks; no auto-removal/time shifts; different weekday settings resolved exactly; unchanged program times and other dates.
- Concurrency: two program operations sharing dates/people; simultaneous I3b save; new dated plan after preview; Trainer ending/Owner revocation both lock orders; last place/overlap; same operation concurrent/replayed with changed payload.
- Recovery: interruption before/after each staged write and date commit; unknown response; check original operation; confirmed save/read failure; reload/resume private preparation; cancellation/activation races; commit visible only as all reviewed dates, never counted twice. Injected failures after first/middle/last date or audit write roll back the entire live change.
- Privacy: two academies; platform-only/wrong roles; foreign branch/date/player/Trainer; revoked membership; forged scope/version/proof/cursor; direct tables/helpers; stale actor tab/late response clearing; names-only projections, no contacts/salary/family data in audit/logs.
- UX: EN/AR320/360/926/1440; keyboard, real phone/touch and screen reader separate; pointer/keyboard Back/reopen, long names, no overflow; loading/pending/empty/denied/stale/partial failure/recovery; every attempted action has a truthful outcome.
- Proposed measurable targets: visible input feedback<=100ms; warm first usable summary/page p95<=2s; page payload<=24KiB/25 rows; SQL page p95<=100ms, review chunk<=150ms, atomic activation target<=300ms (subject to scale feasibility) with3s statement/2s lock ceiling. Record50 observations, declared device/network, cold versus warm and20/40/100/1000-date datasets with large selected rosters. These are targets, not passed evidence. Program summary counting itself must have an explicit bound/query plan; duration bounds alone do not bound work.
- Cost: record reads/writes/SQL time/response bytes per reviewed/applied date and per unchanged/preserved date; no full-roster polling, unbounded fanout, added queue service, paid upgrade or dependency without a demonstrated need. Sustained multi-academy fairness and operational capacity remain separate gates.
