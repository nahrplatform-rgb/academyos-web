# I3c — connected program/date planning design and engineering preparation

27 October2026. Proposed contract. [Policy recommendations](i3c-program-planning-decisions.md) await Owner decision. No functional implementation, migration, deployment or new access grant is claimed by this document. Current program/date source remains intact.

## Connected interaction

1. **Training / Programs.** Existing saved program summary retains full period, per-weekday times and ready state. Primary **Plan the program**, secondary **View dates**. No program-planning action on an incomplete program. Published/operational controls remain absent.
2. **Program planning / Choose scope.** Readable whole-period summary; optional range/weekday subset. Explain existing date plans will be preserved. Separate collapsed “Different choices by weekday” editor. Show capacity, optional Trainer and bounded player search/selected-roster builder using existing shared controls. Clearing a field is explicit; no guessed capacity. A Trainer search failure is not an empty candidate list.
3. **Review dated changes.** Summary counts ready/preserved/blocked; actual date rows show branch timezone/time, current versus proposed capacity/Trainer/roster count, changed-player detail on demand and conflict reasons with only authorized fields. Filter by status; stable pagination, all scope accounted for. Counts alone do not substitute for dated preview. **Inspect individual plan** opens current I3b date details and preserves return context. Changed proposal invalidates the review. No preselected conflict waiver.
4. **Exact confirmation.** “Apply to37 dates; preserve1 individual plan; leave2 blocked dates unchanged.” Explain completed dates stay saved if interrupted. A checkbox confirms that concrete scope; button says **Apply to37 dates**. All-preserved or all-blocked has correction/inspection actions and no apply button.
5. **Applying / paused / unknown.** Show durable operation progress and exact completed/remaining/blocked counts. No browser-only counter treated as committed. Navigation away preserves original operation reference. Resume/pause/cancel affect future work only and never imply rollback. Ambiguous response offers **Check original operation**. Revocation clears private projection and stops further writes.
6. **Result / next action.** Show completed and remaining dates separately; **Review remaining dates**, **View dates**, **Open saved plan**. Owner-only draft state remains prominent. Individual save updates only its date; later program proposals preserve it by default. No synthetic success toast for blocked or preserved work.

Desktop retains sidebar → program/date work list → contextual inspector; no nested inspector stacking or OS window controls. Phone uses full-width scope/review/detail steps with consistent Back; return restores program, scope, filter/page and selection. EN/AR translations include counts, mixed-result wording, timezone and status labels; use logical layout, bidi-safe time/code,44px phone targets and keyboard focus on changed step. Reuse `WorkspaceShell`, `WorkspacePanes` and native controls. Prototype simulations, if built, must be visibly labeled and never use actual account data or provider calls.

## Trust boundaries and bounded reads

Current identity → same-origin staging API → named bounded caller transport → current Owner/academy/branch/ready program → private proposed snapshot/job/dated planning/audit. No cached permission or public RPC execution alone is authority. Reuse existing gateway/limiter, canonical Trainer lifecycle lock order, UTC half-open conflicts, version checks and direct-table denial. Extending trusted RPC allowlists requires exact route/proof tests. No generic privileged proxy or internal HTTP loop impersonating the Owner.

Proposed retrieval: program/scope summary independent of first dated page; dated preview25 rows plus sentinel, stable saved-date order/cursor; conflicts/current-roster details on demand, each25 rows; candidate search25 plus sentinel with latest-query cancellation; request<=8KiB and response<=24KiB per ordinary page. Large selected rosters are private staged selections with bounded edit requests and exact count/version, not client-fetched academy directories. Freeze proposal and date-set identity server-side; bind actor/academy/branch/program/scope/proposal fingerprint. Cursor/key includes that full scope, never only program ID.

Private reads no-store; current permissions rechecked on each read/write/continuation. Revalidate people/date versions and cross-date conflicts on execution. Any materially changed eligibility/scope or newly blocked date pauses future work for fresh review. Completed dates remain immutable historical operation results. UI may show that its reviewed state is stale; it must not assert it is still conflict-free. Poll only while visible/active, coalesce focus/reconnect, back off on failures, no automatic provider write merely from rendering. Review token, expiry and server job processing mechanism are engineering decisions to validate; they cannot broaden scope or leave authority cached for later processing.

## Atomicity, recovery and migration design criteria

Preserve one date's capacity/Trainer/full intended roster/history/audit as an atomic unit. Do not expose a partially built staged roster as an active date plan. Snapshot candidates/versions and an operation ledger support interrupted preparation, unknown replies and at-most-once date effects. All stages retain current-authority checks; already ended Trainer stays ended. The same operation with different scope/roster must conflict. Use canonical academy lifecycle lock first; deterministic date order, operation locks and version guards avoid cross-date overlap races and save/end deadlocks. Program progress has explicit committed per-date counts, no independent unverified increment.

Before implementation, measure maximum safe per-transaction preparation/commit work and introduce bounded staging if a large roster cannot fit current SQL timeouts. Do not promise whole-program atomicity. No arbitrary28-day duration or25-player program cap. If measured limits prevent this contract, revise the design openly before implementation. Rehearse forward migration on a fresh restored encrypted staging backup; no schema removal or destructive rollback of existing date plans. Recover/reconcile original operations before replacement or environment repair.

## Test and performance acceptance plan

- Policy: whole period, smaller subset, weekday-specific values; exact target counts; preserve existing plans; all-preserved/all-blocked empty action; date edit remains independent; program retry cannot overwrite it.
- Correctness: every committed date matches its review; explicit ready-subset apply; deterministic duplicate/overlap/capacity checks; no auto-removal/time shifts; different weekday settings resolved exactly; unchanged program times and other dates.
- Concurrency: two program operations sharing dates/people; simultaneous I3b save; new dated plan after preview; Trainer ending/Owner revocation both lock orders; last place/overlap; same operation concurrent/replayed with changed payload.
- Recovery: interruption before/after each staged write and date commit; unknown response; check original operation; confirmed save/read failure; reload/resume only remainder; cancellation races; committed work retained and never counted twice. Injected child/header/audit failures roll back the whole affected date.
- Privacy: two academies; platform-only/wrong roles; foreign branch/date/player/Trainer; revoked membership; forged scope/version/proof/cursor; direct tables/helpers; stale actor tab/late response clearing; names-only projections, no contacts/salary/family data in audit/logs.
- UX: EN/AR320/360/926/1440; keyboard, real phone/touch and screen reader separate; pointer/keyboard Back/reopen, long names, no overflow; loading/pending/empty/denied/stale/partial failure/recovery; every attempted action has a truthful outcome.
- Proposed measurable targets: visible input feedback<=100ms; warm first usable summary/page p95<=2s; page payload<=24KiB/25 rows; SQL page p95<=100ms, review chunk<=150ms, date commit<=300ms with3s statement/2s lock ceiling. Record50 observations, declared device/network, cold versus warm and20/40/100/1000-date datasets with large selected rosters. These are targets, not passed evidence. Program summary counting itself must have an explicit bound/query plan; duration bounds alone do not bound work.
- Cost: record reads/writes/SQL time/response bytes per reviewed/applied date and per unchanged/preserved date; no full-roster polling, unbounded fanout, added queue service, paid upgrade or dependency without a demonstrated need. Sustained multi-academy fairness and operational capacity remain separate gates.
