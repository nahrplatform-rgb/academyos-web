## Scanner and concurrent-session journey

1. Owner sees one branch's selected published sessions, Trainer sees only own assigned published sessions. Preview has Jordan's17:00 football, Taylor's17:15 swimming and Jordan's18:00 football. These sessions are fictional; no new hosted publication. Back-to-back Morgan belongs to17:00 and18:00 football; the underlying sessions do not overlap, but30-minute scanning margins do.
2. Automatic or exact-session selector stays visible with current branch timezone, saved scan window, inherited/overridden indication and eligible-session count. Select scope once. Current-authority server matching in implementation must cover the whole matching scope, not infer uniqueness from a partial page. No general day-only attendance. Mark key is the stable occurrence/player, not player/day or program alone.
3. Start scanner opens the contextual task. Prototype explicitly simulates camera permission/unavailable states and uses `DEMO-1-R1` etc typed codes instead of pretending to decode real cards. Real camera requires explicit Start and browser permission; stop tracks on leaving/context changes. No image upload, tracking or background scanning.
4. One valid roster/window/actor match → auto-submit Present with no per-player confirmation. Pending pauses capture; design-review “Finish simulated response” above the app resolves its simulated reply. Only confirmed saved result updates register/count/history, names the exact session and rearms. Code entry represents the same untrusted input, not a privileged alternate endpoint. Real server eligibility/window/card recheck is required.
5. Multiple matches → pause, identify player and show only exact eligible session choices. Choosing one records only it, not every candidate. Choice applies to this scan only. No match/invalid/foreign card → nothing saved, actionable retry/select/manual path. Exact-session mode cannot bypass roster, permissions or window. Trainer must not see the other Trainer's session or private player samples.
6. Repeated Present → Already recorded, no new mark/history. Saved Absent → pause and link existing canonical correction workflow; QR never silently flips it. The prototype's register/correction context is a simulation/reference to already implemented correction behavior, not a second correction implementation.

## Windows and settings

Owner settings: minutes before session start and after session end, default30/30.17:00–18:00 accepts16:30–18:30. Percentage sizing is not the default. Owner can edit academy defaults or select a session override. Exact review names target, values and consequences; confirmed save applies them together. Existing explicit overrides survive a default change; non-overridden sessions use current defaults, including future sessions. Stored attendance/history never recalculates because a window changes. Changing settings should invalidate scanner match/context, and commit checks current saved settings.

QR can record early arrival before session start; manual recording/correction still starts at session start and ends24 hours after effective end. Existing manual function must not be weakened to obtain early QR behavior. Server owns capture method/policy, identity/academy, effective occurrence time and window. Before-start/after-window QR denial, moved/canceled/unpublished/withdrawn session and role/revision changes need independent authoritative tests.

Proposed first implementation input range: whole minutes0–180 on each side; zero allows session-bound scanning, wider-than-three-hour extensions need a reviewed policy change. This upper bound remains a recommendation pending Owner confirmation; the preview currently demonstrates nonnegative whole-minute settings without treating arbitrary inputs as an approved production rule. Clock/date/overnight arithmetic must use real timestamps and date-specific branch timezone; prototype labels are not timezone-runtime evidence. Future bulk overrides, settings change scheduling and per-sport defaults remain later scope.

## Card lifecycle — proposed for review

Current Owner only → select registered fictional player → issue/replace/revoke → review consequence → pending → confirmed current state. One current card; valid until revoke/replace, no automatic expiry proposed. Replacement invalidates prior code atomically. Card possession grants no login/private browsing; scan result itself is permission-scoped. Prior attendance/history remain. Prototype renders visibly non-scannable demo codes, not generated QR images or usable credential secrets. Owner-only print/save delivery is intended; real QR generation/print rendering and protected raw credential recovery are still implementation/design-detail gates, not proven by this text card.

Lost issuance/replacement reply must reconcile original operation before replacement. If the raw printable code cannot be recovered safely after confirmed issuance, explicitly replace the original under current authority; do not invent a second active card or show a fake printable result. No public-card route/email/Guardian card projection, bulk issuance, expiry default, real child data or staff-card presence is authorized by this review.

## Failure/recovery and verification

Loading/read failure hide current roster/match and say that retrieval is unavailable rather than empty. Current denial clears private data. Camera denial/unavailable offers typed-card/manual fallback. Invalid/ambiguous/Absent/current-state-changed results pause; no loop of repeated rejected writes. Current read changes, actor/session scope and simulated time change reset active scanning/match. Dirty settings navigation asks before discarding; language preserves drafts. Pending/unknown blocks scope/actor/scenario change and replacement capture. Confirmed-write/read failure offers result read only; lost reply checks original once; not-committed result must be fenced before a replacement attempt. These are design simulations, not actual SQL concurrency or cancellation-fence proof.
