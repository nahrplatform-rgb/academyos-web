### What each evidence layer establishes

| Evidence | Scope and required distinction |
|---|---|
| Source review | Implementation, ownership and potential failure path; a timing hypothesis remains a hypothesis until exercised |
| Utility test | Function classification/output for the supplied inputs; no automatic component, navigation or lifecycle proof |
| Component/hook integration | Real component/hook/handler with controlled external dependencies and observable operational state; simulated state outside that implementation is insufficient |
| Routed journey | Actual destination components and entry/action/return exercised, including relevant focus, context, locale and request budget; a correct href or the same fixture component at every URL has narrower scope |
| Server/data fixture | Named signed operation, transaction/authority/recovery boundary under its declared synthetic environment; no implicit hosted identity or installed proof |
| Hosted/installed | Exact deployed source and declared identity/device/container behavior actually observed; installation, private data coverage and working acceptance remain separate |
| Structural validator | Required fields/joins, source freshness or generated-text consistency only; it cannot certify that a receipt's prose describes a behavior its tests exercise |

For each affected behavior, the coordinator maps the completion claim to its actual assertion and checks that the test can detect the failure. For a known regression, demonstrate a suitable negative control against the old behavior or an isolated broken variant. Do not alter unrelated working source or fake a failure. If the hypothesis does not reproduce, record that result and narrow the claim. A comment that a state transition "would run here", an aggregate pass count or a success-shaped mock does not replace the assertion. A document calling a utility test "integration" does not change its scope.

Retain keyboard coverage on the original affected control alongside appropriate pointer coverage. Do not substitute testing a different control. A delayed advisory operation must be exercised through the real lifecycle when claiming that it cannot block or overwrite operational state, including relevant denial, scope-change and unmount outcomes. Keep existing unknown-original and dirty-state guards.

## Batch contract

A batch has one useful user outcome linked to the [VAL catalog](product-outcomes.csv), a finite set of related journeys/screens/actions, canonical and reference joins, accepted-versus-pending policy, affected trust/storage/migration boundaries, baseline and measurable acceptance, one coordinator and a compatible rollback/forward-repair. Explain how it saves effort, improves understanding or enables controlled delegation; justify mandatory fields/steps/reviews and simplified/replaced legacy mechanisms using the [value specification](product-outcomes-and-simplicity.md). The [batch catalog](delivery-batches.csv) gives scope and dependencies; the [single tracker](../experience-execution.csv) owns current execution/status. Batches are not deadlines or automatic implementation approval.

`MP-B01` is the current coherent Owner-day batch. Subsequent batches complete setup/resources, training, attendance, family/development, finance and the other product families with their applicable redesign/local-data work. New schemas/policies are addressed within the affected batch; do not turn supporting architecture into another endless prerequisite phase. Conversely, a known permission/ledger/original-loss defect blocks the dependent change, not all independent product work.

The catalog is the initial dependency-aware order, not a rule that an unanswered finance decision stops independent Platform/support/design work. If a whole current batch genuinely cannot advance, record the exact blocked scope, select a ready independent batch, explicitly reorder the existing primary rows, move the blocked row to queued and designate one new current row. Preserve IDs/dependencies/evidence and explain the reprioritization. Do not mark the blocked batch passed merely to satisfy routing or automatically skip an unmet prerequisite. Within a batch, continue already-authorized independent work first.
