## Batch contract

A batch has one useful user outcome linked to the [VAL catalog](product-outcomes.csv), a finite set of related journeys/screens/actions, canonical and reference joins, accepted-versus-pending policy, affected trust/storage/migration boundaries, baseline and measurable acceptance, one coordinator and a compatible rollback/forward-repair. Explain how it saves effort, improves understanding or enables controlled delegation; justify mandatory fields/steps/reviews and simplified/replaced legacy mechanisms using the [value specification](product-outcomes-and-simplicity.md). The [batch catalog](delivery-batches.csv) gives scope and dependencies; the [single tracker](../experience-execution.csv) owns current execution/status. Batches are not deadlines or automatic implementation approval.

`MP-B01` is the current coherent Owner-day batch. Subsequent batches complete setup/resources, training, attendance, family/development, finance and the other product families with their applicable redesign/local-data work. New schemas/policies are addressed within the affected batch; do not turn supporting architecture into another endless prerequisite phase. Conversely, a known permission/ledger/original-loss defect blocks the dependent change, not all independent product work.

The catalog is the initial dependency-aware order, not a rule that an unanswered finance decision stops independent Platform/support/design work. If a whole current batch genuinely cannot advance, record the exact blocked scope, select a ready independent batch, explicitly reorder the existing primary rows, move the blocked row to queued and designate one new current row. Preserve IDs/dependencies/evidence and explain the reprioritization. Do not mark the blocked batch passed merely to satisfy routing or automatically skip an unmet prerequisite. Within a batch, continue already-authorized independent work first.

## Three verification levels

| Level | When | Required work | Consolidation |
|---|---|---|---|
| Edit/contract check | During implementation | Focused type/lint/tests and actual outcomes for changed behavior; relevant access/versions/transaction/recovery cases; inspect generated field pipeline | Do not run every unrelated browser/DB suite for each small edit |
| Coherent batch checkpoint | A connected candidate is ready, or a high-risk boundary requires earlier evidence | Combined relevant regressions, integrated EN/AR/task/role/sport checks, appropriate full suite, factual captures/HTML and documentation validators | One reviewed coherent push/candidate; preserve failures and repair causes |
| Release/working review | Exact checked candidate is promoted by Owner | Independently verify exact live source, declared signed-in flows and important changed states; actual installed/device checks where claimed; Owner acceptance | One consolidated walkthrough per meaningful release, not one per control |

Existing required CI assertions and public-repository workflow protections remain. A source push may trigger one full unprivileged PR validation plus established main/manual checks. Do not buy runners, install one on the Owner's Mac, disable tests or alter provider/branch controls to save time. Batch local commits and coherent pushes to reduce redundant full runs; documentation tooling changes need their meaningful checks, while unchanged product suites can be reused honestly. This task itself runs documentation/generator checks only.

Do not postpone discovery of a broken permission, atomic write, crypto/key transition, migration or original-operation boundary until after many dependent changes. These checks stay close to the edit. Once unchanged checks pass, repeat them only for a new change, failure or unresolved risk. A broad regression at the checkpoint is still required where the source release gate requires it.

For a harness consuming root `.next` HTML/chunks, first run root `npm run build`. The build wrapper records unchanged-before/after source hashes and compiled public-shell/static-asset hashes; the consuming fixture rejects a missing, stale or mixed build. The four negative/freshness checks run in the existing CI traceability step. Source-only receipt freshness cannot certify compiled assets. The [8 November MP-B01 correction](../../07-handoff/mp-b01-owner-feedback-continuity-2026-11-07.md#8-november-corrected-compiled-runtime-evidence) records the observed mixed-build gap and repair. ## Acceptance dimensions and realistic fixtures

Every batch selects representative combinations of role, academy, branch, sport, locale, viewport/container, connection, volume and workflow state. Use risk-based combinations and shared regression coverage rather than rerunning the full Cartesian product for each button. Record exact cases and untested combinations. Required examples include:

-18-player register: direct labelled marks, summary/save, dirty return, history, correction, unknown/retry and version/window/role changes.
-40-date program: weekday times, automatic full bounded checks, mandatory exceptions, preserved individual plans, exact publish audience/counts, move/cancel/history.
-Rich player record: create/edit/reopen, conditional sport fields, duplicate comparison, profile overview, Guardian scope and import validation/completeness as supported.
-Two academies/two different sports: correct terminology/resources/filters, no cross-scope list/count/export/local original, pending A command after B switch.
-Guardian next-session and published development: only linked child and published fields; future Scheduled distinct from recorded attendance.
-Offline restart/reconnect: local transaction and original survive;401/session restoration distinct from actual denial; exactly one accepted result or protected refusal/conflict.
-Financial batches: immutable versioned arithmetic examples, currency/rounding, duplicate/provider/payout/review races and exact ledger reconciliation.
