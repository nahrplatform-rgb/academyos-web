## Security/action design before implementation

Clerk creates and verifies OTPs. Subscribe one staging-instance webhook to `email.created`; use the installed Clerk SDK `verifyWebhook` for raw-body signature and timestamp verification. Bind payload `instance_id` to the inspected AcademyOS Staging instance. Handle only the `verification_code` template when `delivered_by_clerk=false`; native-delivered and unrelated templates are acknowledged without sending. A separate server-only bounded recipient allowlist contains the two already authorized test mailboxes. Preserve the invitation sender's existing one-recipient configuration.

The route reads at most 64 KiB including streamed bodies, accepts JSON POST only, exposes no code or event payload in responses, uses no-store/no-referrer, and catches errors without provider/request logging. Existing Sentry privacy settings drop bodies, headers, free-text errors, breadcrumbs and traces. Do not capture OTP-bearing provider screens or copy OTP subjects into docs. Native provider webhook/email retention still applies; no promise of removing their own delivery logs.

For a valid fresh event, render a fixed bilingual staging-only verification message from the existing AcademyOS sender with Clerk's six-digit code; never forward arbitrary event HTML, links, subject or sender. Require the exact inspected instance, email object/id/slug/destination/code shape, and original event age under nine minutes with at most 30 seconds future skew. Do not send expired/retried historical messages. Rate limit per hashed recipient with the existing Redis, fail closed on limiter timeout. One Resend request per attempt with ten-second timeout. Use a stable SHA-256-derived key from Clerk's email id, within Resend's 24-hour idempotency window; event age is much shorter. Concurrent/unknown outcomes retry the same key and payload; no replacement send is generated by this endpoint. Provider acceptance is distinct from inbox receipt. No OTP, recipient or email body is persisted in the app database/cache; Redis holds existing hashed rate-limit state only.

Rollout: inspect template/webhook contract; implement and test forged/tampered/old signatures, wrong instance/recipient/type/template, oversized streaming, invalid code, duplicate/concurrent request key stability, provider unknown/failure, retry and stale event. Deploy handler and server-only secret/allowlist first. Verify unsigned hosted denial, configure subscription, then disable native delivery for only this template after endpoint readiness. Other templates remain unchanged. Ask the recipient to request a fresh code and verify provider acceptance/inbox/Clerk verification separately. No code is read back or entered by the agent. Recovery: re-enable Clerk native delivery for this template and disable the webhook endpoint; retain verified identity/membership/history. The original iCloud rejection can recur under native fallback.
