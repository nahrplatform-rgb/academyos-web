## What changed

- Both private APIs require a registered Owner, academy, event, browser installation and namespace. The [additive migration](../../supabase/migrations/20261104013632_owner_register_bound_transport.sql) checks membership and the exact slot under the existing academy lock before calling the canonical transfer or attendance operation. The application gateway and database retire the unbound private RPCs. Ordinary online attendance still uses its existing permission and receipt contract.
- The [inactive device lifecycle](../../apps/web/src/lib/owner-register-pilot.ts) uses a browser lock and a generation marker for one scoped registration. The marker contains only the routing identifiers and cleanup status. The encrypted store owns key use, rows and immutable pending operations. Logout and known denial fence access before removing the read copy. Interrupted cleanup leaves a sealed or masked state and can be retried. A withdrawal removes the saved read copy while allowing the same current Owner to recover protected pending work. No role or access is assigned by the browser.
- The browser checks the server verification anchor when it opens the prepared copy or starts an operating action. A completed signed roster check can renew it. Thirty days without verification clears downloaded rows and their reusable keys. A clock rollback detected against the last observed browser time requires a new online check. These checks do not impose an inactivity lock. Elapsed time across shutdown depends on the browser clock. Deliberate clock changes, storage eviction and an unlocked origin remain independent security concerns.
- Scope headers sit outside the saved body. An interrupted sync can still reconcile its original ID and exact bytes. An operation already accepted by the server can finish after local departure. A late response cannot restore the old browser view.

## Evidence and request cost

The updated 15-case suite uses real Next handlers, the Supabase SDK and signed gateway, disposable PostgreSQL 17, Chromium and browser IndexedDB. Clerk identity, rate-limit decisions and PostgREST HTTP are fixture adapters. The six new cases cover exact slot denials and closed legacy grants, offline capture and exact replay, clock rollback and 30-day cleanup, membership denial versus publication withdrawal, cross-tab logout racing the first key grant, and interrupted cleanup followed by same-account recovery. The separate real Next Owner working-day fixture continues to cover 18-player EN/AR flows, process restart, deadlines and signed replay. Its second scenario uses a separate fictional academy to keep the one-event rule intact.

First prepare of the two-player fixture used four requests for the key grant, manifest, page and completion. An unchanged check used one manifest. Covered offline reads and capture made zero requests. Exact retry after losing the reply produced one database operation, one mark, one history row and one audit entry. Each scoped transfer or dispatch uses one signed RPC attempt. These are local counts with fixture providers. They do not establish latency percentiles or hosted service costs.
