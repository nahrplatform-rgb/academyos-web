# EX-13B workspace device lifecycle and resumable sync

The local Owner workspace adapter now joins verified account entry, personal-device approval, key release, protected storage, bounded sync and logout. It uses the existing x21 endpoints and the [protected repository](ex13b-workspace-repository-checkpoint-2026-11-05.md). The normal Players and Calendar components are the next integration point. They still use their existing reads in the current app.

| Boundary | Implemented behavior |
|---|---|
| [Device slot](../../apps/web/src/lib/workspace-device-slots.ts) | An explicit approval reserves one locator scoped to the verified subject and academy. Only IDs, mode and generation live in local storage. An incomplete key release can resume against the same device. Read data and key material stay in the protected repository. |
| [Account fence](../../apps/web/src/lib/register-device-account.ts) | The existing account marker fences both capabilities before clearing either. Workspace slots retire their read keys and ciphertext. The attendance path quarantines its replicas and retains pending originals for same-account recovery. Cleanup failure keeps the account fenced for retry. |
| [Browser transport](../../apps/web/src/lib/workspace-client-transport.ts) | Uses exact same-origin endpoints, size-bounded JSON, a cancellable response deadline and scoped receipt checks. The repository owns row hashing before commit. Explicit gateway denial retires the slot. A missing session, generic edge refusal, rate limit and unavailable network can leave compatible copies available. |
| [Sync coordinator](../../apps/web/src/lib/workspace-device.ts) | One browser tab holds the academy sync lock. Another tab can read committed coverage and resume when the leader releases the lock. Cleanup uses a separate lock so a blocked download cannot hold logout. The caller supplies the scope and route lifetime. Broadcasts carry a change signal with no record data. |
| Progress and replacement | People or the requested Calendar month comes first, followed by the other current dataset and adjacent months. A pass fetches at most 12 data pages and resumes from the last committed prefix. An expired receipt renews the compatible prefix. An incompatible manifest clears old coverage before a subsequent rebuild. |

The 12-page limit gives the foreground task a predictable place to yield. A large initial preparation needs another manifest on each pass. The normal route still needs to schedule these passes in response to current task, reconnect and rate limits. The lock protocol uses availability checks instead of queueing a duplicate request. Browser process suspension can delay failover until a holder releases or loses its lock. [Web Locks specification](https://www.w3.org/TR/web-locks/)

The [local transport and browser receipt](evidence/ex13b-workspace-transfer/transport.json) records 24 checks using the actual application transport and signed PostgreSQL boundary. After a held second page was cancelled, another Chromium tab continued from 25 rows. A 326-player fixture paused at 300 rows and renewed an expired continuation before finishing. Compatible reopening made one manifest request and downloaded zero pages. Covered local interactions used zero operating requests in that fixture. The test also covers request priority on Calendar entry, scope changes, transient failure, confirmed denial and a first key response held across shared logout.

The [attendance startup regression](evidence/owner-register-workspace-2026-11-04.json) passed all eight checks, including interrupted logout cleanup, same-account recovery of both pending originals, and Arabic offline startup. Those cases use the existing protected register route. The new fixtures test the Owner data adapters with synthetic identity and disposable PostgreSQL. They do not establish normal-route offline startup, device coverage, hosted latency or independent review.
