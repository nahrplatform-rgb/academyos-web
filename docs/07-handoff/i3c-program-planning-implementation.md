## Result and implementation

Ready saved program → Plan the program → whole-period or explicit range/weekday scope → shared or weekday-specific capacity/optional eligible Trainer/fictional players → saved private proposal → bounded dated review/preparation → exact confirmation → one all-or-none save. Existing date plans remain unchanged. Plan this date still uses the existing I3b operation. Prepared proposal/roster rows are not effective date plans. Reload can reopen saved preparation; lost replies reconcile/fence the original operation. A failed final activation changes no included date.

[Workspace](../../apps/web/src/components/program-planning-workspace.tsx), [bounded contract](../../apps/web/src/lib/program-planning.ts), [staging API](../../apps/web/src/app/api/program-planning/route.ts), [migration](../../supabase/migrations/20261027020000_i3c_atomic_program_planning.sql). Four private RLS tables add proposals, staged weekday player sets, dated target/version snapshots and actor-scoped operation results. Five named RPCs use existing signed caller proof and current Owner/setup/program authority. No direct client tables/helpers, privileged client identity, new account/grant, invitation, provider or dependency. Current branch/timezone and actual immutable UTC intervals remain authoritative.

Create freezes the exact selected saved dates and existing plan versions under the existing academy lifecycle lock. Initial requests accept up to25 players per weekday; larger rosters can be staged through explicit25-change requests, with no total roster capacity or28-day period rule inferred. Staged roster edits invalidate all preparation. Review/preparation handles25 dates per explicit continuation, marking preserved/blocked/current states without effective writes. It is durable private progress, not partial business completion.

Final activation takes the same academy lifecycle lock as individual saves and staff ending; rechecks current Owner/branch/ready program, every target version, full target-set count, staged player scope, current Trainer eligibility, capacity and actual UTC overlaps. Selected people and staff membership/appointment rows are locked. Only after complete validation does one transaction insert all new plans/rosters, advance proposal state, store its operation result and write audit. Existing plans are never updated. First/middle/last child failures and audit failures roll back every new plan and roster. No activation-pointer rewrite of existing I3b reads was required.

Current read pages25+sentinel; response includes exact staged counts, minimal names/IDs, expected versions and preserved current summaries. No contact/family/payroll fields. Candidate queries reuse existing same-branch scoped names-only reads. Proposal state is keyed by identity/academy/program, late requests abort, denial clears private values, and unknown operations retain only scoped opaque IDs. No raw payload telemetry/audit. Audit references the private immutable committed proposal/targets; individual edits retain their existing history. Cancellation before activation prevents all changes; a cancellation racing activation observes serialized current version/state rather than undoing committed plans.
