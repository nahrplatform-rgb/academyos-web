## Cross-role and trust-boundary consistency

| Actor/context | Design priority | Authority boundary and source/handoff |
|---|---|---|
| Platform Owner | Admission, platform commerce, redacted service impact and incident evidence | No tenant ownership/private content from platform status; M1 grant procedure remains separate. Services values are fictional/unknown, not current provider status. |
| Academy Owner | Setup, people/relationships, program/roster, approval exceptions and finance | Academy/branch/capability checks must be current at server/data commit. Setup-only M1 is separate from operational labs. |
| Manager | Explicit permitted branch/capability work | No new role or implicit approval, financial/compensation access or M1 setup write. Studio's operator/reviewer is an illustrative capability, not an approved manager policy. |
| Trainer | Next assigned dated session, complete roster, draft/unknown/confirmed attendance, evaluations and own statement | Assignment-scoped read/write; no other trainers' compensation. QR/manual parity, revoked access and physical offline remain actual-layer gates. |
| Guardian | Current verified child, next enrolled session, confirmed/corrected attendance and published narrative | Contact save not verification; guardian not payer/consent by default. Other-family/private notes excluded from source projections; actual server checks required. |
| Player | Personal schedule and published goals if eligible | S47 personal/published source plus release concept; D-004 age/account policy remains blocked. No fictional age threshold, public ranking or finance authority. |

Detailed actor, branch, input, commit, side-effect, leaving/refresh/context and recovery contracts are in the batch action documents and page/action matrix. Actions identify accepted versus open policies. A stopped financial calculation, ownership transfer, deletion or activation is a truthful policy boundary, not silently completed behavior.

## EN/AR, desktop and mobile

All connected studio domains have paired EN/AR headings, actions, policy and recovery copy; Batch1/2 have localized journeys. Arabic mirrors with logical CSS; navigation arrows mirror while logos/media do not. Emails/identifiers use directional isolation, dates use Intl with declared academy timezone, and explicit demo units avoid a guessed currency. Technical references/fictional names are preserved; fallback fonts and number formatting still need contextual native review. No native-language acceptance is claimed.

Compact desktop baseline retains system typography,22px heading,11px/31px ordinary controls,6px control radius,8px cards, blue primary, compact sidebar/table/inspector and macOS frame. Phone switches to one task column and44px controls, hides desktop sidebar/inspector and uses explicit navigation/detail pages. Trainer and guardian have dedicated task-first source views. All studio forms and operation states inherit phone layout. Native clients remain N1 concepts, not generated builds.

Source supports focus-visible, skip link, named inputs, error summary focus, deliberate dialogs and non-color status labels. It is not a completed WCAG review: actual keyboard order, modal focus return, native selects, zoom/reflow, contrast, screen-reader announcements, phone soft keyboard and touch/RTL layout must be inspected in a real browser/device. Repeated status/live announcements and some field-level error links require review. No blanket enlargement is adopted without demonstrated evidence.

## Loading, operations and recovery

Every studio domain can reproduce normal/loading/empty/failed/restricted states manually. These are labelled simulation. Batch1/2 preserve more specific pending/invitation/capacity/revocation states. Domain paths add:

- Immutable publication versus draft/revision/withdrawal; no private-note projection.
- Original financial/attendance receipt after local commit with lost response; replacement blocked until check.
- Contract exception and unresolved amounts; scheduled versus effective/restricted plan; proof rejection/resubmission.
- Recipient accepted/suppressed/disabled/unknown; media per-item failure and expiry; internal versus customer support.
- Paired stock transfer; frozen complete-scope export progress/failure/resume/expiry; privacy hold/subsystem-evidence checks.
- Collector versus provider state, actual versus estimated/unknown cost, independent copy versus restore evidence, controlled incident proposal/recovery status.
- Per-row import outcomes, archive/restore preserving history; offline mixed-result concept with revoked-item and conflict handling explicitly unavailable for capture.

Committed fictional state survives current-tab refresh; unsaved form/attendance data is excluded from storage, with studio field drafts only in memory across language/theme changes. These are prototype conveniences, not storage policy for real private records. No network calls, analytics, external submissions, actual authentication, payments, uploads, invitation sends or provider changes. The optional export download contains only60 generated fictional ID/label rows. Prototype operation references are local labels, not proof of production idempotency/concurrency/durability.

## Five-dimension review and independent security gate

For **every major journey**, use its batch contract to assess usability (explain/finish scope), speed (first task-ready view), correctness (current authority/version/data definition), cost (bounded projections/paging/attempts) and recovery (uncertainty/partial/stale/denied). None is averaged into a green score. Budgets in the repository remain proposed until actual declared workload/device/network/sample/percentile measurements. A locally rendered skeleton or manual step cannot prove first-useful latency or service cost.

Security packets must preserve: current server/DB role/tenant/branch/field checks; guardian/payer/consent separation; exact invitation recipient; immutable financial/evaluation/attendance history; atomic expected-version writes and operation/payload binding; outbox and per-item results; private file/download/expiry; worker execution authority; safe logs/audit/containment; restore/deletion reconciliation. Negative cases need two academies, branches and roles, revocation while open, direct API/RPC/object paths, concurrency, stale versions and unknown provider effect. Source-model tests of UI transitions do not satisfy those controls. No existing application security test or assertion was changed.
